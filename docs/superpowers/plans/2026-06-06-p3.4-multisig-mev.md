# P3.4 — Real multisig + MEV-protected execution (executor/ops — deferred)

> The last P3 item is **entirely executor-side / infrastructure** — there is no
> unit-testable decision-engine increment, so it is deferred to the executor +
> ops work, consistent with the fill-deferral discipline used throughout P2/P3.

## Why no decision-engine work
- **Real multisig (retire single-signer).** The decision-engine already targets
  the Safe via `SAFE_ADDRESS` (swap recipient / Aave `onBehalfOf`). Migrating
  from a single signer to a real **Safe (Base) / Squads (Solana)** multisig is a
  signing-infrastructure + ops change in the executor and key management — the
  decision-engine emits the same orders regardless of how they are signed.
- **MEV-protected execution.** Submitting via a private mempool (Base:
  Flashbots-style protect RPC) or Jito bundles (Solana) is an **executor**
  concern. The decision-engine's contribution is already in place:
  - every order carries a slippage-bounded `amount_out_min` / `minOut` (P1 swaps,
    P3.3 LP) — **never a naked zero** — which is the primary MEV defence at the
    decision layer.
  - the `priority="urgent"` channel exists on the envelope for de-risk/forced
    unwinds (P3.2 exit actions emit urgent), bypassing gas throttles.

## What remains (executor + ops, with the fill run)
- ts-executor: route Base submissions through a private/protect RPC; wire the
  Safe multisig signer; the Aave + Aerodrome-LP adapters (the P2.3/P3.3 fill
  counterparts).
- solana-executor: Jito bundle submission; Squads multisig (the P2.6 fill).
- ops: provision the multisig signer set; configure the protect RPC endpoints.

## Decision-engine readiness check (done)
- Orders are slippage-bounded (no naked minOut) — P1.1 swaps + P3.3 LP.
- Urgent priority channel available for de-risk — P3.2 actions map to it at the
  fill-run emission hook.
- Recipient is the Safe (`SAFE_ADDRESS`) — multisig-ready addressing.

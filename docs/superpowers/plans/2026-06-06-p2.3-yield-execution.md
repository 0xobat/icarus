# P2.3 — Stable + wBTC Yield Execution (Aave) + multi-leg routing

> Decision-engine side of yield execution: price + register cbBTC, build
> executor-ready **Aave V3 supply/withdraw** order params, and a pure
> **yield-leg router** that sequences the multi-leg moves (swap→supply,
> withdraw→swap) a rebalance needs when capital lives in a lending venue.
> The ts-executor Aave adapter that *executes* supply/withdraw is the fill-side
> counterpart — deferred to the operator's mainnet-fork run, exactly as the P1
> swap fill was.

## Decisions (autonomous, documented)
- **wBTC on Base = cbBTC** — register `cbBTC` (Base mainnet
  `0xcbB7C0000aB88B473b1f5aFd9ef808440eed33Bf`, **8 decimals**). The allocation
  symbol is `cbBTC` (not `WBTC`) so holdings/target/registry all agree. Sepolia
  has no canonical cbBTC → operators override via env (`CBBTC_ADDRESS`).
- **cbBTC pricing** — pegs ~1:1 to BTC; priced off a `cbBTC/USD` (or `BTC/USD`)
  snapshot key. Add `cbBTC` to the pricing slice via a `BTC` alias
  (`market.prices["BTC"]`), mirroring `WETH→ETH`. The adapter sourcing a real
  cbBTC/BTC feed is the data-layer counterpart (tracked, not built here; unit
  tests inject the price).
- **Lending venue = Aave V3 on Base**, named `"aave_v3"`. The decision-engine
  names the venue; the executor's Aave adapter holds the canonical Pool address
  per chain_id. One venue per asset for now → **net-yield venue *selection* is a
  no-op** (single choice); the selection layer + per-venue caps are **P2.5**.
- **Multi-leg atomicity = sequential saga, not atomic bundle.** Each leg is a
  separate `ExecutionOrder`; **leg N+1 is emitted only after leg N's
  ExecutionResult confirms** (driven by the results-consumer across ticks). No
  multicall/flashloan bundling (keeps the risk gate + PnL isolation per-leg, and
  avoids naked router approvals). P2.3 builds the **pure leg planner**
  (`plan_yield_legs`) + per-leg param resolvers; wiring the saga across
  ticks/results is integration, deferred to the fill run.

## Design
### Registry + pricing
- `order_resolver`: add `cbBTC` to `_TOKENS_BY_CHAIN_ID[8453]`; `__main__`
  `_apply_token_overrides` gains `cbBTC` (env `CBBTC_ADDRESS`/`CBBTC_DECIMALS`).
- `pricing`: `_PRICE_KEY_ALIASES["cbBTC"] = "BTC"`.

### Aave order params — `order_resolver`
- `resolve_supply_params(*, chain, asset_symbol, usd_amount, price_usd, recipient,
  venue="aave_v3", chain_id) -> OrderParams`: `token_in=asset addr`,
  `amount=usd_to_smallest_unit(...)`, `recipient` (Aave `onBehalfOf`),
  `venue`, `extra={}`. action set by the cycle (`"supply"`).
- `resolve_withdraw_params(*, chain, asset_symbol, usd_amount, price_usd,
  recipient, venue="aave_v3", chain_id) -> OrderParams`: same shape; the executor
  burns the aToken for `asset_symbol`. `usd_amount` → smallest unit of the
  underlying. A sentinel `amount = -1` (max) is **out of scope** (full-exit is
  P2.4/P3); P2.3 withdraws an exact sized amount.

### Yield-leg router — new `decision_engine/yield_router.py` (pure)
`plan_yield_legs(plan: RebalancePlan, *, deployed: Mapping[str, bool]) -> list[Leg]`
where `Leg = (action, asset_symbol, usd_amount)`:
- `deployed[symbol]` marks assets normally held in a lending venue (USDC, cbBTC
  → True; WETH → False, it goes to wstETH at P2.4).
- A swap `from→to`:
  - if `from` is deployed → prepend a `withdraw(from, amount)` leg (free the
    funds before swapping).
  - the `swap(from→to, amount)` leg.
  - if `to` is deployed → append a `supply(to, amount)` leg (redeploy proceeds).
- A plain swap between two non-deployed assets → single `swap` leg (unchanged).
- Idle-funds deployment (supplying un-deployed balances with no rebalance) is a
  separate concern → **P2.5/P3** (needs the position reader); not here.

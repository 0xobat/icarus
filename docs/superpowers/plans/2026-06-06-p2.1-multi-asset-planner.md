# P2.1 — Multi-Asset Rebalance Planner (pure logic)

> **Pure decision-engine logic, like P1.3.** New module + tests only; NOT wired into the cycle yet (the cycle migration belongs with P2.2's yield-aware multi-asset holdings, which reshapes holdings into a per-asset USD dict). Backward compatible: the existing 2-asset `RebalanceTarget`/`plan_rebalance` stay untouched until P2.2 migrates the cycle.

**Goal:** generalize the 2-asset (crypto/stable) rebalancer to an **N-asset target**, picking **one corrective trade per cycle** (the CLAUDE.md "one strategy adjustment per decision cycle" rule), routing through the **USDC hub**.

## Design
- **`MultiAssetTarget`** (frozen): `weights: Mapping[str, Decimal]` (asset symbol → target weight, must sum to 1.0 within tolerance), `band: Decimal` (absolute-weight tolerance, default 0.10), `hub: str` (the stable funding asset, default "USDC"). Validate at construction: weights > 0, sum ≈ 1, hub ∈ weights, band ∈ [0, 0.5].
  - Base-first default: `{"USDC": 0.40, "ETH": 0.32, "WBTC": 0.28}`, band 0.10, hub "USDC".
- **`plan_multi_rebalance(*, holdings: Mapping[str, Decimal], target: MultiAssetTarget, est_cost_usd: Decimal, cost_gate_margin: Decimal) -> RebalancePlan`** (reuse the existing `RebalancePlan(action, reason, from_symbol, to_symbol, usd_amount)`):
  1. `nav = sum(holdings.values())`. If `nav <= 0` → hold ("empty portfolio").
  2. Per asset, `weight = holdings.get(asset, 0)/nav`; `drift = weight - target.weights[asset]`.
  3. **Select the single most-out-of-band asset** = `argmax(|drift|)` among assets whose `|drift| > band`. None beyond band → **hold** ("within band").
  4. **Build the corrective trade through the hub:**
     - Breaching asset is a **crypto** asset (not the hub):
       - overweight (`drift > 0`) → **sell**: `from=asset, to=hub`, `usd_amount = drift * nav` (the excess).
       - underweight (`drift < 0`) → **buy**: `from=hub, to=asset`, `usd_amount = -drift * nav`.
     - Breaching asset **is the hub** (USDC itself over/under): the corrective leg is the *most-opposite* crypto asset:
       - hub overweight (crypto underweight overall) → buy the crypto asset with the **most-negative drift**: `from=hub, to=that_asset`, `usd_amount = min(hub_excess, that_asset_deficit)` — keep it one clean swap toward both targets.
       - hub underweight → sell the crypto asset with the **most-positive drift**: `from=that_asset, to=hub`.
  5. **Cost gate** (unchanged from P1): if `usd_amount < cost_gate_margin * est_cost_usd` → hold ("cost-gated"). Else → `RebalancePlan(action="rebalance", from_symbol, to_symbol, usd_amount, reason="<asset> <over|under>weight (drift=...)")`.

## Key decisions (flag on review)
- **One adjustment per cycle** — correct only the single most-out-of-band asset. Converges over cycles; keeps order flow to one swap/cycle; honors the CLAUDE.md rule. (A crypto↔crypto correction takes two cycles via the hub — acceptable given the wide ±10% band → low churn.)
- **USDC hub routing** — every correction is `asset↔USDC`, so we never need direct ETH↔wBTC routes/liquidity. USDC is always the most liquid leg.
- **Single global band** (±10% absolute weight), matching P1. Per-asset bands are a later refinement.
- **Reuse `RebalancePlan`** — no new result type; the cycle/order-resolver path is unchanged.
